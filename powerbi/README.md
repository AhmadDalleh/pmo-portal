# Power BI report (assignment section 7)

The `.pbix` itself has to be built in Power BI Desktop (not generated by code). Everything it needs is in the repository:

| Need | Where |
|---|---|
| Data source | PostgreSQL views created by migration `ReportingViews` (never the CSV files) |
| Four commented SQL queries | `sql/reports/01..04_*.sql` |
| DAX measures (12, copy and paste) | `powerbi/measures.dax` |
| Reconciliation table | `docs/reconciliation.md` |

## 1. Connect
Get data > PostgreSQL database. Server `localhost:5433`, database `pmo_db` (your `.env`), mode **Import**, user `pmo` (or a read-only role). Select these views only:
`dim_date`, `dim_project`, `vw_project_financials`, `vw_task_facts`, `vw_milestone_facts`, `vw_risk_facts`, `vw_cost_facts`, `vw_forecast_facts`.
Needs the Npgsql provider that Power BI prompts for on first connect. Reset the data any time with `scripts/reset-db.ps1`, then Refresh.

## 2. Model (star schema)
```
dim_date  ──┐
            ├─ * vw_cost_facts        (dim_date[date_key] -> txn_date)
            ├─ * vw_forecast_facts    (-> period_month)
            ├─ * vw_task_facts        (-> due_date)
            ├─ * vw_milestone_facts   (-> due_date)
            └─ * vw_risk_facts        (-> due_date)
dim_project ─ 1 -> * vw_project_financials, vw_task_facts, vw_milestone_facts, vw_risk_facts, vw_cost_facts, vw_forecast_facts   (key project_id)
```
- Cardinality one-to-many from each dimension to each fact. **Cross-filter direction: single, dimension to fact.**
- The fact views are **not related to each other**. A slicer on `dim_project[department]` filters every fact through `dim_project`. This is how the join fan-out (spend multiplied by task count) is avoided in the model, the same rule as the SQL CTEs (database-design.md section 7).
- `vw_project_financials` is project-grain (one row per project) and holds budget, spend, EAC; use it for the KPI cards. `vw_cost_facts` is transaction-grain; use it for spend by category and by month.
- Mark `dim_date` as the date table (`date_key`). Hide the foreign-key columns in the fact tables.
- Date slicers only affect date-based facts (spend by month, forecast, due dates). The budget, spend and EAC cards are a snapshot at the reporting date stored in `reporting_settings` (2026-09-30), exactly like the web dashboard's default. To change the date: update that table and Refresh.

## 3. Page "Portfolio overview" (management page)
- Cards: Approved Budget, Actual Spend, Remaining Budget, Budget Utilization %, EAC, Projected Variance, Overdue Tasks, Open High Exposure Risks, Task Progress %. Format AED with thousand separators, percentages with one decimal.
- Visuals: clustered bar Approved Budget / Actual Spend / EAC by `project_code`; line chart Spend (Transactions) by `dim_date[month_start]` with Forecast (Future Months) as a second series; donut Spend (Transactions) by `category_name`; bar Overdue Tasks by `assignee`; table of open high-exposure risks.
- Slicers: Department, Project status, Project, Month (`dim_date`), Cost category (affects the category and month visuals only, not the budget cards: document this on the page).

## 4. Explain in the interview
- Relationship direction: dimension filters facts, never the other way, so a risk slicer cannot change the budget.
- Why views: one definition of overdue / actual spend / EAC for SQL, API and DAX (database-design.md section 6).
- Why the measures return the same value as the dashboard: see `docs/reconciliation.md` and the test `ReportingViewTests`.
